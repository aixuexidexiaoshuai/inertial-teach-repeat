# 没有 GPS、不建图，我用一颗陀螺让小车把同一条路重走了几百遍

> 开源项目：阿克曼小车「里程计 + 惯导」定点巡航（teach-and-repeat）
> 平台：地平线 RDK S100 / X5 + OriginCar 阿克曼底盘 + ICM-20948
> 终点定位精度 **< 4 cm**，航向漂移 **~2° / 6 min**，已在 3 台车上完整复现
>
> 本文是本仓库的配套技术文章 · License: MIT

---

## 0. 先说结论

这套方案要解决的问题只有一句话：**让小车把人开过一遍的路线，之后自己一模一样地重走**。

不用 GPS，不用 UWB，不建图，不贴地标，不巡线。场地就是一片空地。

最后落地的技术选择，可以浓缩成一句反直觉的话：

> **我主动扔掉了磁力计给的"绝对航向"，换来一个每次开机都从 0 开始的"相对航向"。**

听起来像倒退——放弃了绝对参考、放弃了漂移有界。但正是这一步，把复现性从"看运气"变成了"每次都一样"。

这篇文章讲清楚四件事：

1. 为什么定点巡航的命门是**航向**，而不是位置；
2. 纯陀螺方案的**三个病和三个治法**（含全部代码与参数）；
3. 位姿有了之后，用 **Stanley + 曲率前馈**怎么把车贴回线上；
4. 上位机再准，也会被**下位机固件**卡住 —— 我们改了什么，以及还该改什么。

## 1. 定点巡航到底难在哪

teach-and-repeat（示教-复现）的原理朴素得不像话：

```
录制阶段：人遥控开一遍，每隔 2cm 记一个 (x, y, yaw)
回放阶段：车自己沿着这串点走回去
```

难点全在"我现在在哪"上。没有全局定位，只能靠**航位推算（Dead Reckoning）**：

```
位置增量 = 轮式里程计给的行进距离
航向 yaw = 车头朝向 —— 决定这段距离"往哪个方向走"
```

这里有个特别容易被忽略的不对称性：

- **位置 (x, y)** 靠轮速积分，短程内相当准，误差是线性累积的；
- **航向 yaw** 是**误差放大器**，误差会被路程放大。

算一笔账：

| 航向误差 | 走 5 m 后的横向偏差 |
|---|---|
| 1° | ≈ 8.7 cm |
| 3° | ≈ 26 cm |
| 5° | ≈ 44 cm |

留给你的横向容差通常也就十几厘米。**航向错 3°，这趟就废了。**

> 所以整套惯导设计只围绕一个目标：
> **拿到一个每次开机都一致、且不随时间乱漂的航向。**

注意这句话里有两个独立的要求，后面会反复出现：
- **一致**（复现性）：今天开机和明天开机，同一个车头朝向要得到同一个航向值；
- **不乱漂**（稳定性）：跑了 5 分钟，航向不能自己偏出去。

很多方案能满足其中一个，同时满足两个才算过关。

## 2. 三代方案：航向源是怎么被一个个排除掉的

这不是设计出来的，是被实车问题一次次逼出来的。

| 代次 | 硬件 | 航向来源 | 死因 |
|---|---|---|---|
| 一代 | MPU6050（6 轴） | 纯陀螺积分 | 零偏**温漂**压不住，越跑越偏 |
| 二代 | ICM-20948（9 轴，用磁力计） | 磁力计给**绝对航向** | 场地**磁畸变**，航向跳数十度，换个位置就废 |
| 三代 | ICM-20948 **当 6 轴用** | 陀螺积分 + 开机归零 | ✅ 最终方案 |

三个候选航向源的排除逻辑：

```
航向从哪来？
 ├─ 磁力计 → 给绝对航向，理论最优，但赛场钢结构 + 电机磁场 → 跳数十度   ✗
 ├─ 轮速   → 阿克曼模型反算角速度，一打滑就带偏                        ✗
 └─ 陀螺   → 唯一可信 ✓  但它有三个病
```

**轮速这条要单独说一下**，因为它最有迷惑性——底盘本来就在发 `odom`，里面自带 `vyaw`，白给的为什么不用？

我做过一个特别直观的实验：**把车抬起来，让轮子空转（模拟极端打滑），手动把车身转 3 圈（1080°）**。

- 陀螺报：**1083°**（误差 0.3%，非常准）
- EKF 输出：**0.1°**

轮速算出来的 `vyaw` 因为轮子在空转、车身"没动"，把准确的陀螺读数**直接压死了**。EKF 是加权融合，你喂给它一个自信满满的错误源，它就信错误的那个。

**结论：轮速只管位置，绝不让它碰航向。**

二代到三代的转折最值得说。磁力计给绝对航向本来是巨大的优点：冷启动即用、漂移有界、不需要初始对准。但在一个金属结构密集的场地里，它变成了**最大的不确定性来源**——同一个朝向，车停在 A 点和 B 点读数差几十度。

于是做了那个决定：

> **`imu_filter_madgwick` 设 `use_mag=false`。磁力计继续发数据，但被彻底忽略。**

代价写得明明白白：**每次必须在发车点同朝向开机**（开机车头方向 = 航向 0）。

一个必须遵守的开机仪式，换来 100% 的复现性。这笔买卖非常划算。

## 3. 完整信号链

弃掉磁力计后，ICM-20948 只输出陀螺 + 加速度，一条链把它们变成可用的位姿：

```
ICM-20948 ──raw──→ icm20948_driver ──/icm/data_raw──→ imu_filter_madgwick ──/imu/data──→ ekf_node ──→ /odom_combined
(陀螺+加速度)       ①开机标零偏                        ②纯陀螺积分 yaw                    ③只融 vyaw
                    ②ZUPT 治温漂                        加速度只纠 roll/pitch              航向从 0 积分
                                                                                            轮速只管位置
```

| 环节 | 干了什么 | 解决什么 |
|---|---|---|
| `icm20948_driver` | 开机静止标定零偏；运行中 ZUPT 持续校准 | 陀螺零偏 & 温漂 |
| `imu_filter_madgwick` | 陀螺积分出 yaw；**加速度只用来纠 roll/pitch** | 姿态解算，关磁免疫磁干扰 |
| `ekf_node`（robot_localization） | 轮速管位置 + 陀螺 vyaw 管航向，航向**从 0 积分** | 输出统一位姿 `/odom_combined` |

加速度那句要展开一下：加速度计能观测重力方向，所以它能修正 **roll/pitch**（俯仰/翻滚），但对 **yaw** 完全无观测能力（绕重力轴转动，重力矢量不变）。让它只管 roll/pitch 是物理上的正解，也顺手防止了车过坎时俯仰污染航向。

下面逐个治陀螺的三个病。

---

## 4. 陀螺病① 开机零偏 → 开机静止 3 秒标定

陀螺输出 = **真实角速度 + 零偏（bias）**。

零偏不扣掉，车静止时它也在"转"，积分几秒航向就飞了。实测这颗 ICM 的零偏量级：

```
陀螺零偏标定完成(300 样本)：bias 1.88/-1.08/0.09 °/s → 已扣除，开始正常发布
```

**1.88 °/s** 是什么概念？静止 3 秒，航向就假性偏出 **5.6°**——回到第 1 节那张表，这已经够走 5 米偏出半米了。

实现很简单（`icm20948_driver.py`）：开机后前 3 秒（100 Hz × 3 = 300 帧）累加三轴读数取均值，期间**对外发布角速度 = 0**（此刻车必须静止，发 0 比发未标定的脏数据安全）：

```python
if not self.gcal_done:
    self.gsum[0] += gx; self.gsum[1] += gy; self.gsum[2] += gz; self.gcnt += 1
    gx = gy = gz = 0.0                      # 标定期间对外发 0
    if self.gcnt >= self.gcal_n:            # gcal_n = 3.0s × 100Hz = 300
        self.gbias = [self.gsum[i] / self.gcnt for i in range(3)]
        self.gcal_done = True
else:
    gx -= self.gbias[0]; gy -= self.gbias[1]; gz -= self.gbias[2]
```

> ⚠️ **铁律由此而来：标定这 3 秒绝对不能碰车。**
> 碰一下，抖动就被当成零偏累加进均值，整趟航向基准全歪。这是最容易踩、也最难查的坑——因为它不报错，只是让你的车"今天状态不太好"。

## 5. 陀螺病② 绝对航向不可复现 → EKF 只融 vyaw、从 0 积分

**这是整套方案最精妙、也最反直觉的一步，是复现性的根子。**

`robot_localization` 的 `ekf_node` 有 15 维状态，跟航向相关的有两项：绝对 `yaw` 和角速度 `vyaw`。直觉上当然是融合绝对 `yaw` —— 那是"航向"本身啊。

**但恰恰不能融它。**

原因：madgwick 关掉磁力计之后，它输出的绝对 `yaw` 是一个**任意初值**。实测每次开机是 `-127°` 这种毫无规律的随机数（初始四元数由第一帧加速度定姿，yaw 分量完全随机）。融合它，等于把整个系统**锚死在一个随机角度上**——复现性直接归零。

于是配置成这样（`config/ekf_odom.yaml`）：

```yaml
# 15元: [x,y,z, roll,pitch,yaw, vx,vy,vz, vroll,vpitch,vyaw, ax,ay,az]

odom0: odom
odom0_config: [true,  false, false,     # x 用，y 不用
               false, false, false,
               true,  false, false,     # vx 用
               false, false, false,     # ⭐ vyaw 关掉：轮速不许碰航向
               false, false, false]
odom0_differential: true

imu0: /imu/data
imu0_config: [false, false, false,
              false, false, false,      # ⭐ 绝对 yaw 关掉：关磁后是随机初值
              false, false, false,
              false, false, true,       # ⭐ 只融 vyaw：唯一可信航向源
              false, false, false]

imu0_twist_rejection_threshold: 100.0   # ⭐ 默认 1.5σ 太激进，急转会被误判拒收
```

四个关键决策，逐条解释：

| 项 | 设置 | 深层原因 |
|---|---|---|
| IMU 绝对 `yaw` | **关** | 关磁后是任意初值（实测 -127°），融了等于锚在随机角上 |
| IMU `vyaw` | **开** | 唯一可信航向源。EKF 对它积分 → 航向从 0 累积 |
| 轮速 `vyaw` | **关** | 打滑会带偏（前面那个 1080° 实验） |
| 轮速 `vy` | **关** | 阿克曼是非完整约束、根本没有横向速度，底盘却报带标度误差的假 `vy`，融了会往侧向持续累积漂移（实测 B 环 1.68m 误差几乎全在 Y 方向） |
| `imu0_twist_rejection_threshold` | 1.5 → **100** | 马氏距离 1.5σ 拒收阈值太紧，急转时真实高转速和 EKF 保守预测差得远，被**当成异常值扔掉**（就是前面转 1080° 只认 78° 的元凶之一）。放开后航向忠实跟陀螺 |

那个 `vy` 的坑也值得单独记一笔：**底盘发出来的数据不一定符合它自己的运动学**。阿克曼车物理上不可能有横向速度，但底盘固件照样报一个带噪声、带 1.125 标度的 `vy`。这种"看起来有、实际不该有"的量，融进去就是纯污染。

### 为什么"从 0 积分"就解决了复现性

```
录制时：开机 → 静止 3s → yaw 基准 = 0 → 录轨迹（起点 yaw ≈ 0）
回放时：开机 → 静止 3s → yaw 基准 = 0 → 跑轨迹（起点 yaw ≈ 0）
        └────────────── 两次的坐标系天然重合 ──────────────┘
```

**不需要任何初始对准，不需要找绝对北。** 只要在同一个位置、同一个朝向开机，录制坐标系和回放坐标系就自动对齐——开机时的车头方向被锚定为 X 轴。

这就是那句核心哲学的落地：**用"相对复现性"替代"绝对定位"**。

**还有一个白送的好处**：`base_footprint → imu_link` 的 TF 用**单位阵**就行，完全不用标定 IMU 安装角。IMU 装歪了、有个恒定倾斜，效果只是把整个 odom 坐标系旋转一个固定角度——而录制和回放用的是**同一个歪掉的坐标系**，误差自动抵消。

唯一需要实车确认的只有 **yaw 的符号**：左转时 yaw 应该增大，如果反了，把 `gyro_z_sign` 翻成 `-1.0`。

## 6. 陀螺病③ 零偏温漂 → ZUPT 零速更新

开机标定一次就够了吗？不够。

**零偏不是常数**。芯片一升温，bias 就慢慢漂。实测换新 IMU 后温漂达到 **-1.3 °/min**——开机标得再准，跑 5 分钟也偏出 6°。

治法是 **ZUPT（Zero-velocity UPdaTe，零速更新）**：只在**确认真静止**的时候，把残留的零偏一点点"吸"进 bias 估计里，让它跟着温度走。

```python
if self.zupt_enable:
    # 三轴扣偏后角速度都小于阈值 → 认为静止
    if abs(gx) < self.zupt_thresh and abs(gy) < self.zupt_thresh and abs(gz) < self.zupt_thresh:
        self._still_cnt += 1
        if self._still_cnt >= self.zupt_win:        # 连续静止 0.5s 才允许更新
            self.gbias[0] += self.zupt_ema * gx     # EMA 0.01，时间常数 ≈ 1s，极缓慢
            self.gbias[1] += self.zupt_ema * gy
            self.gbias[2] += self.zupt_ema * gz
    else:
        self._still_cnt = 0                         # ⭐ 一动就立即冻结，绝不更新
```

参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `zupt_gyro_thresh_dps` | 1.5 °/s | 静止判据。取在噪声峰（~0.57 °/s）之上、真实转动（>5 °/s）之下 |
| `zupt_window_sec` | 0.5 s | 需连续静止这么久才开始更新 |
| `zupt_ema` | 0.01 | 每帧的跟踪率，时间常数 ≈ 1 s |

**设计精髓在 `else` 分支**：一旦任意一轴超阈（说明车在动），静止计数**立即清零**。

如果不这么做，转弯时的真实角速度会被当成"零偏"吸进去，越校越错，直接把系统搞崩。ZUPT 的全部安全性都建立在"我确信现在是静止的"这个判断上，所以判据必须保守——**宁可少校，不可错校**。

好处是这个校准完全免费：发车前的等待、任务段之间的停顿，都会自动触发。

> **实测效果：航向漂移压到 ~2° / 6 min。**
> 单次任务只有几十秒到几分钟，漂移量落在厘米级误差内；而且 teach-and-repeat 是录制和回放**同样慢漂**，还能部分自抵消。

### 三个病三个治法，一张图收尾

```
                    陀螺是唯一可信航向源，但它有三个病
       ┌────────────────────────┼────────────────────────┐
    病① 开机零偏             病② 绝对航向不可复现        病③ 温漂
    静止时也在"转"            关磁后是随机初值            越跑越偏
       │                        │                          │
    治① 开机静止 3s 标定     治② EKF 只融 vyaw、从 0 积分  治③ ZUPT 静止校准
       ▼                        ▼                          ▼
    积分干净                 每次开机航向恒从 0          漂移压到 2°/6min
                                │
                   每次开机一致、且不乱漂的可信航向  ✓
```

## 7. 位姿有了，怎么走回线上：Stanley + 曲率前馈

第 3~6 节解决的是"**我在哪、朝哪**"（estimation）。接下来是"**怎么走回录制的路**"（control）。这是自动驾驶的经典分野，合起来才是完整的定点巡航。

### 7.1 找最近点：只在前方一个小窗口里找

每个控制周期，先在录制路径上找离车最近的点作为跟踪目标。

**关键：只在 `progress_idx` 前方 8 个点的窗口里找，不做全局搜索。**

为什么？因为路径经常有**折返**（比如作业点的三点掉头）。全局找最近点，车走到折返处会一下子"跳"到对面那条腿上，进度瞬间乱套，车直接飞出去。限定在前方小窗口里单调前进，就杜绝了跨腿跳点。

（顺带一提，窗口大小必须**远小于折返的索引跨度**，否则窗口自己就跨过去了。2cm 一个点的密集采样在这里帮了大忙。）

### 7.2 两个误差

设最近点为 P，其路径切线方向为 `tan`、录制时的车头朝向为 `face`：

| 误差 | 含义 | 计算 |
|---|---|---|
| 横向误差 `e` | 车偏离路径的垂直距离（左正右负） | `e = (x−px)·(−sin tan) + (y−py)·(cos tan)`，即把车到 P 的位移**投影到路径法线**上 |
| 航向误差 `he` | 车头与路径的夹角 | `he = face − yaw`，归一化到 ±π |

一句话：`e` 是"我离线有多远"，`he` 是"我车头歪没歪"。Stanley 要同时把两个都消成 0。

### 7.3 控制律

```
δ = heading_gain · he  +  atan2(−k·e, ks+v)  +  curv_ff · atan(L·κ)
    └──── 航向项 ────┘   └──── 横向项 ────┘   └──── 曲率前馈 ────┘
```

**① 航向项**（`heading_gain` = 1.0）：车头歪了就打舵掰正，对齐路径切线。

**② 横向项**（`stanley_k` = 1.2，`stanley_ks` = 0.4）：Stanley 的精髓。偏离路径就产生一个"往回打"的转角。

- `k` 越大纠偏越狠，**过大会发抖**（高速直线上出极限环）；
- `ks` 是**软化项**，分母 `ks+v` 让纠偏力度随速度自适应：低速时（v→0）防止 `atan2` 过冲把方向打死，高速时又不会过激；
- 用 `atan2` 而不是普通除法，天然把转角限制在 ±90°，且 v=0 时数值稳定。

> **相比 Pure Pursuit 的优势**：Stanley 直接盯着横向误差消偏，贴线精度更高，正好对上"厘米级复现"的需求。Pure Pursuit 的前视距离本质上是在"抄近道"，弯道内切明显。

**③ 曲率前馈**（`curv_ff_gain` = 1.4）：前两项都是**反馈**——等误差出现了才纠，弯道上必然**滞后**，弯越急偏越多。

而录制路径上每一点该弯多少（曲率 κ）是**已知的**，直接把舵先打出来就行：由阿克曼运动学，曲率 κ 对应的前轮转角就是 `atan(L·κ)`。加了前馈之后，`e` 和 `he` 退化成微调，只补舵机延迟和漂移。

> **实测意义**：不加曲率前馈，仿真里弯道滞后达 **12.5 cm**——对厘米级复现来说这已经是致命的。加了之后弯道贴合明显改善。
>
> 注意：**只在前进段加**。倒车段是三点掉头的尖点，κ 无定义，那里交给航向反馈。

### 7.4 转角 → 底盘指令

算出的前轮转角 δ 不能直接发，因为下位机（STM32）把 `cmd_vel.angular.z` 当**角速度 ω** 读：

```
δ ──阿克曼运动学──→ ω = v · tan(δ) / L
        /cmd_vel: linear.x = v, angular.z = ω
        STM32 按 R = v/ω 反解阿克曼转角驱动舵机
```

发出去之前还要过三重"体检"：

| 环节 | 作用 |
|---|---|
| 转角限幅 | δ 夹到物理极限（本车左 0.320 rad / 右 0.446 rad，左右不对称） |
| 舵角低通 `alpha_delta` | 高速直线极限环摆动时滤波（0.3~0.5，越小越稳、弯道越钝） |
| 舵角斜率限幅 `delta_rate_max` | 限制每周期舵角变化率，同样治极限环 |

### 7.5 速度规划

转角决定往哪打，速度决定多快走：

| 机制 | 参数 | 作用 |
|---|---|---|
| 基础巡航 | 0.20 m/s | 直线段速度 |
| 过弯减速 | `turn_slowdown` = 0.6 | 转角越大越慢 |
| 末端减速 | `end_slow_dist` = 0.30 m | 按距离线性降速，贴准终点 |
| 加速度限幅 | `accel_max` = 1.5 m/s² | 消除速度突跳 |
| 倒车限速 | `reverse_max_speed` = 0.12 m/s | 倒车是盲区，慢且稳 |

**忠实倒车**是个容易被忽略的细节：录制时如果人倒过车，回放也必须倒着走，否则轨迹对不上。判据是每个点的**录制车头 yaw 与运动切线方向是否相反**（`cos < 0`）；前后换向时先停稳再走（阿克曼换向必须停）；另外实测底盘倒车的转向符号与运动学模型相反，软件端要翻 `-1.0`。

### 7.6 完整回放流程

```
录制(waypoint_capture)              回放(odom_waypoint_follower)
  遥控开一遍                            每周期 50Hz：
  每 2cm 记 (x, y, yaw) ──→ smooth_path ──→ ① 前向窗口找最近点
                            平滑成曲线      ② 算 e, he
                            + 算曲率 κ      ③ Stanley: δ = 航向 + 横向 + 前馈
                                            ④ δ→ω，限幅/滤波 → /cmd_vel
                                            ⑤ 速度规划（过弯/末端/倒车）
```

精度保障：终点位置误差 `final_tolerance` **< 4 cm**，可选加航向门；进终点区（<10cm）如果卡住超过 2s 强制停车，防止撞板空转烧电机。

## 8. 上位机再准，也会被下位机卡住

前面七节都在讲上位机：位姿估计和控制算法。但 `/cmd_vel` 发出去之后，**真正把转角变成舵机 PWM、把速度变成电机转速的是下位机固件**。这一层不对，上面算得再准也白搭。

本项目对 STM32 固件做了两处改动，都是被实车问题逼出来的。

### 8.1 已改①：舵机转向对称化

**症状**：同样大小的转角指令，车**左转打得少、右转打得多**。

**根因**在固件的舵机映射公式里：

```c
// 改前
Angle_Servo = -0.628f*pow(AngleR,3) + 1.269f*pow(AngleR,2) - 1.772f*AngleR + 1.573f;
Servo = SERVO_INIT + (Angle_Servo - 1.572f)*Ratio;

// 改后：只保留奇次项
Angle_Servo = -0.628f*pow(AngleR,3) - 1.772f*AngleR;
Servo = SERVO_INIT + Angle_Servo*Ratio;
```

映射左右对称的数学条件是**奇函数**（只含 x、x³… 奇次项）。原公式里的**偶次项 `+1.269·AngleR²`** 和常数项正是破坏对称的根源。删掉它们、保留原厂标定的一/三次项（那是舵机-连杆的真实非线性），对任意转角都严格对称，且 `AngleR=0` 时精确回中位。

| 前轮转角 | 旧 PWM | 新 PWM | 新公式偏离中位 |
|---|---|---|---|
| +0.32（左最大） | 1209 | 1126 | −374 |
| 0（直行） | 1500 | 1500 | 0（精确居中） |
| −0.32（右对称） | 1957 | 1874 | +374（与左严格对称） |

旧公式在 ±0.32 处左偏 −291 / 右偏 +457，**差 167**；新公式左右严格相等。

**为什么这对 Stanley 很重要**：控制器内部**假设"转角指令 → 实际转角"是对称的**，它用同一套增益处理左偏和右偏。固件不对称，就等于左右两侧的等效增益不同 —— 一侧偏强、一侧偏弱，左弯右弯贴合精度不一致，teach-and-repeat 的复现性被系统性地打折。

> 附带收获：对称化后 −0.49 rad 算出 PWM=2100，不再撞 2200 的限幅上限（旧公式是 2294 → 被削到 −0.4461）。本仓库的 `steer_max_right_rad` 保守起见仍填 0.4461，**你可以重新实测把右侧放宽到 0.49**。

### 8.2 已改②：串口上报 20Hz → 50Hz

```c
// HARDWARE/usartx.c 的 data_task（向上位机发里程计 + IMU 原始数据）
vTaskDelayUntil(&lastWakeTime, F2T(RATE_20_HZ));   // 改前
vTaskDelayUntil(&lastWakeTime, F2T(RATE_50_HZ));   // 改后
```

波特率 115200 不用动（50Hz × 24 字节 = 1200 B/s，余量 10 倍）。

**为什么要改**：整条链是 `下位机上报 → EKF → follower`，而 follower **直接用最近收到的位姿、不做时间戳外推**。链上任何一环慢了，控制就在用陈旧位姿算 Stanley。所以三者必须对齐：**下位机上报 50Hz、EKF `frequency: 50.0`、follower `control_rate: 50.0`** —— 少改一个，另外两个的收益就被卡死。

### 8.3 还该改：把"安全"从上位机的软约束下沉为固件的硬保证

这几条我们没来得及做，但**优先级排第一的那条，强烈建议你先做**：

| 问题 | 现状风险 | 建议方案 |
|---|---|---|
| **无失联保护（最高优先级）** | 固件的 `command_lost_count` 被注释掉了，速度是全局变量、只在收到串口数据时更新 ⇒ **上位机一退出，底盘保持最后的速度继续跑**（实测：Ctrl-C 打断巡航，车一直冲出去） | 加 **cmd_vel 看门狗**：超过 N ms 没收到指令自动零速刹停 |
| 转向模型不统一 | 厂商通用阿克曼转换与 STM32 实际模型不等价，上位机被迫按固件模型反解 ω（就是 `_omega_for_delta` 那段） | 固件内统一转向模型，上位机只发 ω，杜绝双重换算 |
| 里程计精度 | 轮速里程计有累积标度误差 | 标定轮径/轮距，编码器加温补 |
| 控制周期抖动 | 串口通信偶发延迟，上位机无从对齐 | 固件侧固定控制周期，**加时间戳**供上位机对齐/外推 |
| 急停依赖上位机 | 停车靠上位机主动发零速 | 固件级硬急停：急停按钮直连 MCU 中断 |
| 倒车转向符号 | 需要上位机用 `reverse_steer_sign=-1.0` 补偿 | 固件内统一正负逻辑，消除软件端的补偿 |

上位机侧的兜底（本仓库已实现）：节点退出时**连发 5 次零速**再 `destroy_node`（单次 publish 可能还在 DDS 队列里就被销毁了）。但这只是兜底 —— **进程被 kill -9 时它一样不执行**。看门狗必须在固件里。

> **一句话：安全不能只靠上位机的自觉。**

## 9. 工程铁律（血泪换的）

### 惯导使用

1. **发车点严格同朝向开机** —— 航向从 0 起算，朝向错了整条轨迹偏。
2. **开机头 3 秒静止别碰车** —— 陀螺零偏标定期，动了标定就废，而且不报错。
3. **IMU 必须平放固定** —— 安装姿态影响积分基准；松动比装歪更可怕（装歪能抵消，松动不能）。

### 硬件

4. **I²C 地址锁死在配置里** —— AD0 引脚接触不良会让地址在 0x68/0x69 之间随机跳，表现为"有时候起不来"。配置锁定 + 修排线。
5. **串口按序列号绑 udev 别名** —— 底盘和另一个 USB-CDC 设备抢 `/dev/ttyACM0`，谁先枚举谁赢，随机崩溃。按序列号绑成固定别名（如 `/dev/origincar_base`）彻底解决。

### 部署调试

6. **参数改动同步所有方案** —— 多车、多路线、多套 yaml，只改一处等于埋雷。
7. **部署前先 diff 车上版本** —— 本地落后会被静默覆盖；反过来忘了同步，会拿旧版本测出"假故障"，白查半天。
8. **测试节点用完杀干净并复查** —— 孤儿进程抢 `/cmd_vel`，车会自己乱跑。这个已经酿过事故了。


**不包含**：与具体赛题绑定的任务编排脚本。

### 依赖

本仓库按下面这套硬件写死（参数与转向契约都是实测值）：

- OriginCar 阿克曼底盘（STM32F407ZG 下位机，ROS 包 `origincar_base`）+ **改过的固件**（第 8 节）
- 地平线 RDK S100 / X5，ROS 2 Humble
- ICM-20948 挂 i2c-5（地址 0x68 或 0x69）
- `robot_localization`（`ekf_node`）、`imu_filter_madgwick`（**务必 `use_mag:=false`**）
- Python：`numpy`、`scipy`、`matplotlib`（仅平滑工具需要）

### 上车前的一次性确认

方案在 3 台车上移植验证过（2×RDK X5 + 1×RDK S100），沉淀出两个向后兼容参数，
一套代码适配不同板子：

| 参数 | 作用 |
|---|---|
| `imu_addr` | 不同模块 I²C 地址不同（X5 那台是 0x69，S100 这台是 0x68） |
| `gyro_z_sign` | IMU 装反时翻转 yaw 符号（+1.0 / −1.0） |

要过一遍的只有四件事：

1. **I²C 地址**：`i2cdetect -y 5` 确认是 0x68 还是 0x69；
2. **yaw 符号**：起 `odom_monitor`，原地左转，方向角应当增大，反了就翻 `gyro_z_sign`；
3. **倒车转向**：录一段带倒车的轨迹回放，打反就把 `reverse_steer_sign` 翻成 +1.0；
4. **速度调参**：从 0.2 m/s 起，先把直线跑稳（`stanley_k`），再调弯道（`curv_ff_gain`）。

> 换别的底盘时，唯一必须动的代码是 `_omega_for_delta()` —— 它按**本车固件的模型**
> （`R = Vx/Vz`，再 `AngleR = atan(Axle/(R+0.5·Wheel))`）反解 ω。底盘若直接读转角就
> `return delta`；若用教科书自行车模型就 `return v·tan(δ)/L`。搞错这一环车会诡异地转圈。

### 快速上手

```bash
# 1. 编译
colcon build --packages-select ahpu_odom_nav

# 2. 一键起全链路：底盘 + 惯导 + EKF（⚠️ 开机后 3 秒内别碰车）
ros2 launch ahpu_odom_nav bringup.launch.py imu_addr:=104

# 3. 录制：遥控开一遍（s 开始 / q 结束）
ros2 run ahpu_odom_nav waypoint_capture --ros-args -p path_name:=my_route

# 4. 平滑 + 算曲率，并出一张路线图先确认
ros2 run ahpu_odom_nav smooth_path path_my_route.yaml 0.02

# 5. 回放（把车放回原位，同朝向重新开机）
ros2 launch ahpu_odom_nav odom_nav.launch.py params_file:=$PWD/path_my_route_smooth.yaml
```

## 12. 写在最后

回头看，这个项目最有价值的不是任何一段代码，而是那个取舍：

> **当"绝对"不可靠时，"可复现"比"准确"更有用。**

磁力计给的绝对航向理论上更优——有绝对参考、漂移有界。但在一个磁场被钢结构搅乱的场地里，它的"准确"是随机的。而纯陀螺方案明明有累积漂移这个致命缺陷，却因为**每次开机都以完全相同的方式漂**，反而成了那个能稳定重复的方案。

teach-and-repeat 的本质是"重复"，不是"定位"。想明白这一点，剩下的都是工程。

后面还想继续挖的方向：长时间任务（>10 min）引入加速度计辅助的航向重锚；用温度传感器直接补偿陀螺零偏，减少对"必须有静止时刻"的依赖。

代码就在本仓库，用法见 [README](../README.md)。有问题欢迎开 issue。
